一次检查自己的 API 服务时，我遇到了一个很容易让人困惑的现象：网站打不开，请求一直转圈，但登录服务器查看时，应用、反向代理、数据库和缓存服务都显示在运行。

当时很容易下意识怀疑 DNS、证书或者网络。可继续往下查发现，这次更值得注意的线索在服务器的资源限制里：应用所在的 cgroup 出现了很严重的内存回收压力。

这是 2026 年 10 月 23 日的一次现场记录。服务名和数值对应当时的环境，不能直接照搬成其他机器的推荐配置。

## 现象：进程活着，请求却没有回来

当时的观察大致是这样：

| 检查位置 | 观察结果 |
|---|---|
| 公网 DNS | 域名解析到了服务器 |
| 公网连接 | TCP 可以建立，TLS 握手超时 |
| 服务器本机 | 回环地址的 HTTP、HTTPS 健康检查也超时 |
| systemd | Sub2API、Caddy、PostgreSQL、Redis 均显示 active |
| 内核记录 | 没看到近期 OOM kill |
| 连接队列 | 8443 端口的 accept 队列出现积压 |

“公网打不开”不一定是公网网络的问题。当我发现**服务器自己访问自己的服务也超时**时，排查重心就应从外部链路转向本机：应用能否处理请求、代理是否响应、资源是否被限制。

同时，服务状态显示 active，只能说明 systemd 认为进程还在；它不能替代真实请求，更不能证明进程没有因等待资源而几乎无法工作。

## 真正异常的地方：内存压力

这台机器给 Sub2API 所在资源组配置了两条 systemd 内存限制：

~~~text
MemoryHigh=256M
MemoryMax=320M
~~~

排查时，资源组的 `memory.events` 中 `high` 计数已经累计到约 1370 万；`memory.pressure` 的一个快照里，`some avg10` 约为 98.72，`full avg10` 约为 73.41。

这几个数字不能单独拿来当作“某次故障的完整证明”，但结合本机请求超时和其他现象，它们指向了很明显的资源压力。特别是 `high` 是**累计事件计数**，看它是否持续增长，比只看一个大数字更有帮助。

按照 [Linux 内核对 cgroup v2 的说明](https://docs.kernel.org/6.9/admin-guide/cgroup-v2.html)，超过 `memory.high` 时，相关进程会受到限制并参与直接内存回收；这条限制本身并不直接触发 OOM killer。换句话说：**没有 OOM kill，不代表没有严重的内存压力。**

[PSI（Pressure Stall Information）](https://docs.kernel.org/accounting/psi.html)则用于观察资源争用带来的停顿。排查时应结合 `some`、`full` 和不同时间窗口看趋势，不要把单个快照当成全程平均值。

## 我是怎样验证这个方向的

确认当时的设置后，我先在运行时把这个资源组的 `MemoryHigh` 从 `256M` 提高到 `320M`；`MemoryMax` 保持 `320M`，没有重启服务。

调整后，本机和公网健康检查很快恢复。随后我把相同的 `MemoryHigh` 值持久化，再做短期复验：

- 公网健康检查和登录页面返回 HTTP 200；
- `memory.events` 里的相关计数在复验时没有继续增长；
- 内存压力快照明显下降；
- 应用和其他服务没有因为这次处理而重启。

这些现象支持“内存回收压力与这次超时密切相关”的判断。但此次记录没有完成全国多点复测，也没有跑真实模型请求或持续负载测试，所以我不能把它写成“所有场景都已经彻底恢复”。

另外，调整后高水位已经与硬上限一样。它解决了当时的紧急问题，却没有凭空增加机器内存，也不是长期容量规划；服务接近硬上限时，仍需结合真实负载评估资源。

## 如果下次再遇到，我会先看什么

先做几层区分：

1. **域名和公网连接**：DNS 解析是否正确，连接卡在哪一步？
2. **服务器本机**：通过回环地址访问健康检查，是否也会超时？
3. **服务状态**：进程是否在运行，日志和连接队列有什么异常？
4. **资源限制**：除了内存使用量，还要看 cgroup 的限制、事件计数和压力变化。

在使用 cgroup v2、服务归属关系明确的 Linux 主机上，可以先查看 systemd 中配置的资源组信息：

~~~bash
systemctl show sub2api.slice -p ControlGroup -p MemoryHigh -p MemoryMax
~~~

再根据输出的 `ControlGroup` 路径，查看对应 cgroup 下的 `memory.events` 和 `memory.pressure`。不同系统、服务和层级的路径可能不同；要先确认自己查看的是正确的资源组。某些环境也可能没有启用相应的压力统计。

至于是否调整限制，需要同时考虑机器剩余资源、同机其他服务、峰值负载和回滚方案。把我的 `320M` 复制过去，并不能保证另一台服务器更稳定。

## 这次排障给我的提醒

这次最容易误导人的，是“所有服务都是绿色的”。它们确实没有退出，但用户的请求也确实没有得到响应。

以后我会把进程状态、真实健康检查、资源限制和压力指标放在一起看：**进程在，服务能响应，业务请求能完成，是三个需要分别验证的问题。**
