最近维护自建 AI 中转服务时，我碰到一个挺绕的问题：有用户说，使用同步方式生图时可以看到图片，换成另一种流式调用后，客户端却只显示文字，图片没有出现。

更奇怪的是，服务端并不是完全没有反应：有的请求返回了 HTTP 200，使用记录里也出现了图片输出。那到底是没生成，还是生成了但没传到客户端，又或者客户端收到了却没展示？

我把 2026 年 11 月 17 日的排查过程整理下来。**这篇文章目前是一份未完成的故障记录**：服务端的部分调用已经验证，但当时那台 Windows 客户端没有展示图片的最终原因，还没有确认。

## 最开始：请求直接返回 403

一开始的问题比较明确：用户尝试调用生图能力时，接口返回 403。检查中转服务配置后发现，请求所属用户组的生图权限没有开启。

把该组的相关权限打开后，至少排除了这一次 403 的直接原因。但当时并没有立刻完成真实图片生成验证，所以也不能因为开关打开，就断定所有客户端都能正常看到图片。

这提醒我把“有权限”与“整条调用链可用”分开看。一个请求要走完，除了分组权限，还可能涉及上游账号、模型、接口格式、中转服务和客户端本身。

## 两条看起来相似、实际不同的调用路径

这次涉及的两种路径可以简单理解为：

~~~text
直接图片接口：
客户端 → /v1/images/generations → 图片生成 → 返回图片数据

对话中的图片工具：
客户端 → /v1/responses → 对话模型调用 image_generation → 返回工具结果
~~~

这只是用来理解本次问题的简化图。具体可用模型和参数，应以使用时的[图片生成接口文档](https://developers.openai.com/api/docs/guides/image-generation)、[对话生图工具文档](https://developers.openai.com/api/docs/guides/tools-image-generation)、账号权限和中转实现为准。

当时我查看使用记录发现：用户说的“同步成功”与“流式未展示”，不仅传输方式不同，**使用的接口和模型也不同**。因此，光凭这两条记录，不能得出“问题一定是流式传输导致的”这个结论。

为了让部分 Codex 请求能带上生图工具，我还检查并开启了中转服务对应账号的 Hosted 生图桥接。这个设置影响的是符合条件的请求如何携带工具，并不自动保证网络传输或客户端展示一定正常。

## 服务端有记录，不等于客户端看到了图

排查时，服务端日志中出现过一次 HTTP 200，使用记录也显示产生了一张图片。这个结果只能说明请求在服务端侧留下了成功和用量相关记录。

当时的使用日志没有保存实际图片内容，因此它不能回答下面两个问题：

1. 图片数据是否真的到达了用户那台 Windows 电脑？
2. 客户端拿到数据后，是否正确解析并显示？

我之前也差点因为“模拟请求成功”，就把结论说成“客户端应该可以展示”。后来对照用户截图，才意识到这个推断超出了测试范围。

HTTP 状态、用量记录、响应体和用户看到的界面，是不同层次的证据。某一层成功，并不能自动替下一层作证。

## 中间还遇到了上游认证过期

为了对比同步与流式，我准备做一组控制变量测试。第一次尝试时，上游账号的令牌已经过期，同步请求先收到了认证失败；随后中转服务暂时把该账号置于冷却状态，紧接着的测试也无法形成有效对比。

这组失败不能拿来证明流式模式有问题。它只说明当时的认证状态不足以支持那次实验，继续比较其他变量也没有意义。

后来重新登录后，账号恢复可调度，我才继续做下一轮测试。整个过程也让我意识到：排查服务时，测试本身可能改变账号状态；每做一步，都要记录时间、对象和它对后续实验的影响。

## 重新登录后，控制变量再测一次

在服务端，我用**同一个图片接口、同一个图片模型和相同尺寸及质量设置**，分别测试了非流式与流式请求。两次都返回 HTTP 200，也都收到了能识别为 PNG 的完整图片数据。

接着我模拟了一次 Codex 的流式 Responses 请求：响应里能看到生图完成事件、图片数据和整个响应的完成事件。再让请求从服务器本机经过 Caddy 的 HTTPS 代理，结果也能收到完整图片。

这几组测试能证明什么？

| 测试结果 | 能说明 | 不能说明 |
|---|---|---|
| 同一图片接口的同步和流式均返回 PNG | 当时的服务端测试中，两种方式都能返回图片数据 | 用户电脑的对应界面一定能显示 |
| 模拟 Codex 请求收到完成事件 | 模拟请求的服务端响应包含相应事件和数据 | 真正的 Codex 客户端一定按同样方式处理 |
| 经过本机 Caddy 的 HTTPS 测试通过 | 本机代理路径下的测试响应完整 | 经过公网到 Windows 客户端也一定完整 |
| 客户端截图没有图片 | 用户看到的结果确实没有展示图片 | 图片一定在服务端生成阶段丢失 |

尤其要注意：经过 Caddy 的那次测试，仍是在服务器本机发起，并没有覆盖用户电脑的公网连接和实际界面。

## 下一步应该继续查什么

如果要继续缩小范围，我会在不记录密钥和用户私有图片的前提下，补齐下面这些信息：

1. 确认实际客户端版本、操作系统和调用方式；
2. 用相同接口、模型、图片参数及网络路径做同步与流式对照；
3. 在客户端侧确认是否收到关键完成事件和图片结果，而不仅仅看服务端用量；
4. 对照是否经过了不同代理、不同账号或不同权限组；
5. 记录每次实验的时间和配置变化，避免把两次条件不同的结果直接比较。

如果只是临时需要生图，已经在服务端验证过的图片接口可以作为一个待客户端验证的替代方向；但替代方案也需要在实际使用的电脑上确认，不能只看服务端测试结果。

这次经历让我对“成功”这个词更谨慎了一点：**服务端成功、网络返回成功和用户看到结果，是要分别验证的三个环节。**
